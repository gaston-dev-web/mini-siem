# Incident notes

Analyst practice notes and analysis reports written against alerts raised by
this SIEM.

**Where the data comes from — read this first.** Two different sources are used
here, and each document says which one it used:

- **Triage notes** (the short ones, `WHAT FIRED` / `WHEN` / …) run on **synthetic
  data** generated by the project's own attack simulator
  (`siem/simulator/generate_logs.py`) — no real systems, no real attackers, no
  real users.
- **Analysis reports** (the long ones) run on **real published capture data**:
  `sample_logs/openssh_real.log`, from the open
  [Loghub](https://github.com/logpai/loghub) dataset. The attackers and IPs in
  those reports are real, but the host is not a system anyone here operates, and
  no action was taken on any of it.

Either way these are exercises in the analysis process, not reports of security
events on systems belonging to the author.

The point of writing them is that detection is only half the job. A SIEM that
fires a perfect alert into a queue nobody can act on has achieved nothing. The
skill worth practising is the one that turns an alert into a decision someone
else can execute: what fired, what actually happened, is it real, and what now.

## The format — triage notes

Each triage note answers six questions in a fixed order:

| Field | Purpose |
|---|---|
| **WHAT FIRED** | Which rule, and at what severity |
| **WHEN** | Time window of the activity, not just the alert time |
| **WHO / WHERE** | Source → destination. The field that says who to block |
| **WHAT HAPPENED** | What the *raw logs* show — never a paraphrase of the rule |
| **ASSESSMENT** | True or false positive, and what the impact actually is |
| **NEXT ACTION** | Numbered, specific, executable by someone else |

Two rules that shape every note here:

1. **Every claim traces to a log line.** No "probably", no "seems like". If the
   note says the activity was automated, it says what makes it automated.
2. **The alert is a doorbell, not a report.** Alert metadata routinely understates
   an incident — a threshold rule fires the moment it crosses the threshold and
   stops counting. The numbers in these notes come from the logs, not the alert.

## The format — analysis reports

An analysis report covers a whole capture rather than a single alert: scope and
data quality, parser coverage, an activity overview, individual findings, a
verdict, **what the analysis could not see**, and recommendations. The verdict is
split per question rather than given as one global answer, so that findings which
can be closed are closed and the ones that remain open carry the action that
would close them.
